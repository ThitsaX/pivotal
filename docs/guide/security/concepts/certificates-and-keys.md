# Certificates and Keys

> Applies to: Pivotal v1.0.1 – v1.3.0, Helm chart 0.2.0 · Profile: both · Document version 1.0 (draft)

## Summary

This page lists every certificate and key used for mTLS and JWS: who creates it, where its private
key is kept, who uses it, and how it is renewed or withdrawn. Other pages link here rather than
repeat these facts. Only two rows change with the key profile: the CA roots and the Hub JWS signing
keys.

## CA roots

- **What:** two separate roots. The **DFSP CA** root for the DFSP-facing side, and the **Pivotal
  Hub-client CA** root for the Hub-facing side.
- **Generated:** in the CA ceremony, inside AWS KMS (`vault-kv`) or AWS CloudHSM (`pkcs11`). The
  private key cannot be exported.
- **Used:** only during the ceremony, to sign the intermediate. No running service can reach a root
  key.
- **Distributed:** the Pivotal Hub-client CA root certificate goes into the Secret
  `pivotal-hub-client-ca`, from which trust-manager registers it in MCM.
- **Lifetime:** 10 years.
- **Renewal:** manual. See [Re-key Pivotal's CAs](../runbooks/common/pivotal-ca-rekey.md).
- **Revocation:** not revocable. Replacing the root is the only remedy.
- **Recovery:** a KMS key cannot be exported or restored outside KMS. A CloudHSM key can be restored
  from a CloudHSM cluster backup.

## Intermediate CAs

- **Generated:** inside Vault during the ceremony, in both profiles. The private key never leaves
  Vault.
- **Signed by:** the matching root, once, during the ceremony.
- **Used:** to sign every leaf certificate Pivotal issues. Vault mount `pki_dfsp` for the DFSP CA,
  `pki_hub_client` for the Pivotal Hub-client CA.
- **Lifetime:** 5 years.
- **Renewal:** manual. See [Re-key Pivotal's CAs](../runbooks/common/pivotal-ca-rekey.md).

## DFSP client certificate

- **Generated:** the DFSP creates its own key pair and a CSR. The key never leaves the DFSP.
  The key must be RSA, at least 2048 bits.
- **Signed by:** the DFSP CA, when an operator submits the CSR in the portal or through the API.
  The certificate is always issued in the DFSP's own FSP ID, whatever name the CSR asks for.
- **Presented by:** the DFSP, on leg 1.
- **Checked by:** the DFSP-facing gateway (against the DFSP CA), then web-outbound, which looks up
  the certificate's fingerprint and checks that it belongs to the DFSP named in `FSPIOP-Source`.
- **Distributed:** trust-manager writes the DFSP CA bundle into the DFSP-facing gateway's namespace.
- **Lifetime:** 1 year, unless `DFSP_CERT_TTL` sets a shorter one.
- **Renewal:** the DFSP submits a new CSR. When the new certificate is issued, the DFSP's existing
  certificates are marked *retiring* and stay valid until they expire, so the DFSP can switch over
  without an outage.
- **Revocation:** an operator revokes it in the portal or through the API. It takes effect on the
  next request, once Pivotal's read replica has the change. While `DFSP_FACING_MTLS_MANDATORY` is `false`, a DFSP that stops presenting a
  certificate is still admitted. See [Revoke a DFSP certificate](../runbooks/common/revoke-dfsp-certificate.md).

## DFSP access key

- **Generated:** by the DFSP. Pivotal never sees the private key.
- **Used:** the DFSP signs each request to web-outbound with it, as a compact JWS in the
  `authorization` header. RS256 only.
- **Checked by:** web-outbound, against the public key registered for the DFSP named in
  `FSPIOP-Source`.
- **Registered:** when the DFSP is onboarded, and replaced through the portal or API.
- **Renewal:** replacing it takes effect within about 5 seconds, with no overlap. The DFSP must
  switch to the new key at the same moment.
- **Revocation:** there is no revoke action. Replace the key instead.

## Hub JWS signing key

- **What:** one RSA 2048 key pair per tenant. Pivotal signs Hub-facing FSPIOP messages with it on
  the tenant's behalf. Not the same key as the DFSP access key.
- **Generated and kept:**

  | Profile | Generated by | Private key kept in | How services find it |
  |---|---|---|---|
  | `vault-kv` | web-pivotal, when the DFSP is onboarded | Vault KV, one path per tenant | Read from Vault |
  | `pkcs11` | A custodian, inside CloudHSM, before onboarding, as the tenant's crypto user. Cannot be exported. Onboarding records its public key. | AWS CloudHSM | A keyRef in Vault; web-outbound signs through key sharing, the connector as the key's owner |
  | unset or `none` | Not created: the deployment does not sign towards the Hub | — | — |

- **Used by:** web-outbound (leg 2) and the tenant's connector (leg 3).
- **Public key:** stored in Pivotal's database, and published to MCM by trust-manager so peers
  (and the Hub, if it verifies) can check signatures. web-outbound signs for a tenant only after
  trust-manager turns signing on, once MCM holds the public key. The connector has no such switch:
  it signs whenever `FSPIOP_USE_JWS=true` and it can read the key.
- **Picked up:** web-outbound re-reads keys every few seconds. The connector reads its key once, at
  startup, and must be restarted after a key change.
- **Renewal and revocation:** not supported in this version. See
  [Known limitations](../known-limitations.md).

## Hub client certificate

- **Generated:** trust-manager creates an RSA 4096 key and a CSR, and enrolls it with MCM. The Hub
  CA signs it. The key never leaves Pivotal's cluster.
- **Kept in:** a Kubernetes Secret (`tls.crt`, `tls.key`), named by `HUB_SERVER_CERT_SECRET_NAME`.
  The setting names say "server certificate"; it is a client certificate.
- **Presented by:** web-outbound and every connector, on legs 2 and 3. One certificate for all of
  Pivotal: tenants are told apart by their JWS signatures, not by certificates.
- **Renewal:** trust-manager checks once a day and renews 30 days before expiry. The old and new
  certificates overlap, so nothing needs coordinating with the Hub. web-outbound and the connectors
  reload the files about once a minute, without a restart.
- **Revocation:** Pivotal cannot revoke it. Ask the Hub operator.

## Hub CA bundle

- **What:** the Hub CA certificate. Public, not secret.
- **Kept in:** the Secret `hub-ca-bundle`, written by trust-manager from MCM. trust-manager checks
  every hour and writes only when it changes.
- **Used by:** web-outbound and the connectors, to check the Hub's server certificate on legs 2 and 3.

## web-inbound server certificate

- **Generated:** by cert-manager, through the `web-inbound-server` role of the Pivotal Hub-client CA.
  The name on the certificate is fixed to web-inbound's public callback host.
- **Kept in:** the Secret `pivotal-web-inbound-hub-tls`, in the Pivotal callback gateway's namespace.
- **Presented by:** the Pivotal callback gateway, on leg 4.
- **Checked by:** the Hub, against Pivotal's CA, which trust-manager registers in MCM.
- **Lifetime and renewal:** set in the cert-manager Certificate resource; the Vault role allows at
  most 90 days. cert-manager renews it. Nothing at the Hub changes, because the Hub trusts the CA,
  not the certificate.

## Hub callback certificate

- **Generated:** MCM creates the key and the CSR. The key stays with the Hub.
- **Signed by:** the Pivotal Hub-client CA (`hub-callback-client` role), by trust-manager.
  trust-manager then has MCM hand it to the Hub.
- **Presented by:** the Hub, when it calls Pivotal on leg 4.
- **Checked by:** the Pivotal callback gateway, against the Pivotal Hub-client CA.
- **Lifetime:** 1 year.
- **Renewal:** trust-manager checks once a day and renews 30 days before expiry, if
  `HUB_CALLBACK_CERT_COMMON_NAME` is set.
- **Revocation:** Pivotal cannot revoke it.

## What this means for you

- Plan for the manual items: the CA roots and intermediates, DFSP client certificate renewals, and
  DFSP access key replacements.
- Watch the automatic ones: see [Check certificate renewals](../runbooks/common/check-certificate-renewals.md).
- Back up the CA material and Vault: see [Backup and recovery](../runbooks/common/backup-and-recovery.md).
