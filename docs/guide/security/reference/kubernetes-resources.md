# Kubernetes Resources

> Applies to: Pivotal v1.4.0 and later, Helm chart 0.3.0 · Profile: both · Document version 1.0 (draft)

Every Kubernetes object that mutual TLS and JWS depend on: who creates it, who keeps it current,
and who reads it. Names in `<ANGLE_CAPS>` are your choice; other names are the defaults or the
names this guide uses.

**Owner** values:

- **Operator, once**: you create it by hand, and nothing changes it afterwards.
- **Operator, once; trust-manager updates**: you create it, and trust-manager keeps its contents current.
- **trust-manager**: trust-manager creates and updates it.
- **cert-manager**: created and renewed from a `Certificate`.
- **Helm**: rendered by the Pivotal chart.

## Secrets and ConfigMaps

Sources: `packages/core/trust/domain/component/hub-ca-sync.scheduler.ts`;
`hub-server-cert.enroller.ts`; `dfsp-ca-publish.scheduler.ts`;
`packages/apps/trust-manager/required.settings.ts`; `docker/pkcs11-entrypoint.sh`;
`helm/templates/trust-manager-rbac.yaml`.

| Name | Namespace | Keys | Contents | Owner | Read by | Profile |
|---|---|---|---|---|---|---|
| `pivotal-hub-client-ca` | Pivotal | `ca.pem` | Pivotal Hub-client CA root certificate, from the ceremony | `vault-kv`: the ceremony script. `pkcs11`: the operator, after each ceremony | trust-manager, through `PIVOTAL_CA_PATH` | both |
| `trust-manager-mcm` | Pivotal | `MCM_CLIENT_SECRET` | trust-manager's MCM client secret | Operator, once | trust-manager, through `valueFrom` | both |
| `hub-server-cert` (set your own name with `HUB_SERVER_CERT_SECRET_NAME`, for example `pivotal-hub-client-cert`) | Pivotal | `tls.crt`, `tls.key` | **Hub client certificate** and its private key. The key is RSA 4096, generated by trust-manager. No `ca.crt`. | trust-manager | web-outbound and every connector, as mounted files | both |
| `hub-ca-bundle` (`HUB_CA_SECRET_NAME`) | Pivotal | `hub-ca.pem` | Hub CA bundle, from MCM | trust-manager | web-outbound and every connector, through `FSPIOP_MTLS_CA_PATH` | both |
| `<DFSP_GATEWAY_CREDENTIAL>` | DFSP-facing gateway's namespace | `tls.crt`, `tls.key` | The DFSP-facing gateway's server certificate for its public host | Operator (usually cert-manager with a public CA) | DFSP-facing gateway | both |
| `<DFSP_GATEWAY_CREDENTIAL>-cacert` (`DFSP_CA_GATEWAY_SECRET_NAME`) | DFSP-facing gateway's namespace | `cacert` | The DFSP CA intermediate (the root stays outside Vault, so it is not published): the anchor DFSP client certificates are checked against | Operator, once; trust-manager updates | DFSP-facing gateway | both |
| `pivotal-web-inbound-hub-tls` | Pivotal callback gateway's namespace | `tls.crt`, `tls.key` | web-inbound server certificate | cert-manager | Pivotal callback gateway | both |
| `pivotal-web-inbound-hub-tls-cacert` | Pivotal callback gateway's namespace | `cacert` | Pivotal Hub-client CA chain, the anchor the Hub callback certificate is checked against | Operator, once (after each ceremony) | Pivotal callback gateway | both |
| `cloudhsm-customer-ca` (ConfigMap; any name, set in `hsmTools.customerCaConfigMap` and the mounts) | Pivotal | `customerCA.crt` | The CloudHSM cluster's CA certificate (public) | Operator, once | the HSM admin pod, and every workload with `CLOUDHSM_IP` set (web-outbound and the connectors), mounted at `/opt/cloudhsm/etc/customerCA.crt` with `subPath`. Without it they stop at startup. | `pkcs11` |

Notes:

- trust-manager **cannot create** `<DFSP_GATEWAY_CREDENTIAL>-cacert`. The chart grants it only
  `get` and `patch` on that one name. If the Secret is missing, the publish fails until you create
  it.
- The chart does not render any `-cacert` Secret. If Helm owned one, every upgrade would reset it.
- An Istio gateway reads its credentials only from its own namespace. Both `-cacert` Secrets must
  be in the gateway's namespace, not Pivotal's.
- The Hub callback certificate itself is not a Kubernetes object. Its key is generated by MCM and
  stays in MCM.

## cert-manager

Sources: `helm/templates/cert-manager.yaml`; `helm/values.yaml` (`certManager`).

| Kind | Name (example) | Renders from | Points at | Produces |
|---|---|---|---|---|
| `ClusterIssuer` | `pivotal-hub-server-issuer` | `certManager.clusterIssuers.items` | Vault `pki_hub_client/sign/web-inbound-server` | — |
| `Certificate` | `pivotal-web-inbound-hub-tls` | `certManager.certificates.items` | `pivotal-hub-server-issuer` | Secret `pivotal-web-inbound-hub-tls` in the gateway's namespace |

Use `sign`, not `issue`, in the issuer's Vault path.

## Istio

Sources: `helm/templates/istio-gateway.yaml`; `istio-virtualservice.yaml`;
`istio-envoyfilter.yaml`; `packages/apps/web-outbound/component/dfsp-certificate.guard.ts`.

| Kind | Name (example) | Owner | Purpose |
|---|---|---|---|
| `Gateway` | `pivotal-dfsp-gateway` | Helm (`istio.gateways`) | DFSP-facing. `tls.mode: OPTIONAL_MUTUAL` while DFSPs move to certificates, then `MUTUAL`. `credentialName: <DFSP_GATEWAY_CREDENTIAL>`. |
| `Gateway` | `pivotal-hub-callback-gateway` | Helm (`istio.gateways`) | Pivotal callback gateway. `tls.mode: MUTUAL`, `credentialName: pivotal-web-inbound-hub-tls`. |
| `VirtualService` | `pivotal-web-outbound-vs` | Helm (`istio.virtualServices`) | DFSP-facing host → web-outbound, port 3200 |
| `VirtualService` | `pivotal-web-inbound-hub-vs` | Helm (`istio.virtualServices`) | Callback host → web-inbound, port 3201 |
| `EnvoyFilter` | `web-outbound-xfcc-forward-only` | Helm (`istio.envoyFilters`) | Sets `forward_client_cert_details: FORWARD_ONLY` on web-outbound's sidecar, so the `x-forwarded-client-cert` header set by the gateway reaches web-outbound unchanged |

web-outbound reads the DFSP's verified certificate only from the `x-forwarded-client-cert`
header. Without the EnvoyFilter, the certificate check on the DFSP-facing leg has nothing to check.

## ServiceAccounts

Source: `helm/templates/serviceaccounts.yaml`.

| ServiceAccount | Created when | Used for |
|---|---|---|
| `web-outbound`, `web-inbound`, `web-pivotal`, `trust-manager`, `app-auditor`, `report-worker`, `portal` | the service is enabled and `serviceAccount.create` is `true` | Vault Kubernetes auth; trust-manager's RBAC |
| `connectors[].serviceAccount.name` | the connector is enabled and `serviceAccount.create` is `true` | Vault Kubernetes auth for that tenant's keys |
| `hsm-tools` | `hsmTools.enabled` is `true` (source: `helm/templates/hsm-tools.yaml`) | Nothing: `automountServiceAccountToken: false`, so the HSM admin pod has no Kubernetes API access |
