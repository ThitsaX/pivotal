# CloudHSM Crypto-User Model — Verified Against Hardware

**2026-09-25.** First run against a real CloudHSM cluster. Everything below was executed on the
device; none of it is reproducible on SoftHSM, which has one user PIN per token and no ownership.

**What this settles:** decision 18 — each tenant's key generated as that tenant's own crypto user,
then shared to the signing user — behaves on hardware the way the design assumed. That was the
largest unvalidated assumption in the HSM-backed profile.

---

## The cluster

| | |
| --- | --- |
| HSMs | 2, Marvell LS2, firmware 10.23 |
| FIPS state | FIPS mode, **single-factor** authentication |
| PKCS#11 slots | **one**, token label `hsm1` — vendor-assigned, not settable |
| PIN length | 8–32 characters |
| Quorum | **not enabled** for user management |
| MFA | none configured on any user |

Single-factor and no quorum together mean `CLOUDHSM_PIN=user:password` is sufficient and one
Crypto Officer can create users alone. Both are assumptions the runbooks make; neither had been
confirmed. **Either could be turned on later**, and both would break the scripts — quorum would
need a second approver at every onboarding, and MFA would break the credential shape entirely.

## The isolation model

Three crypto users: an owner, the shared signing user, and an unrelated tenant. One RSA-2048
keypair generated by the owner and shared to the signing user.

| | sees private key | signs with it | deletes it |
| --- | --- | --- | --- |
| **owner** | yes | yes | yes |
| **shared user** | yes | **yes** | **no** |
| **unrelated tenant** | **no** — public half only | — | — |

The last row is what per-tenant isolation means here, and it is enforced by the device rather than
by configuration: nothing in a policy file or a manifest grants or removes it.

The middle row matters as much. A shared user signs but cannot destroy, so the component that signs
for every tenant cannot take any tenant offline. Delete was refused with *"The current user does not
have adequate key permissions to perform the key operation"*.

**The public half is visible to every crypto user.** That is correct and harmless — it is public —
but it means "the key is listed" is not evidence of access. Only the private label matters.

## What sharing needs

`key share` succeeded with the **owner's** credential. No Crypto Officer is involved, which is what
lets onboarding automate generation and sharing while the one step that needs a custodian — creating
the crypto user — stays manual.

## Defects this run found

Four, all of which would have failed at the first real onboarding.

**Usernames reject hyphens.** Only `a-z A-Z 0-9 _`. Every crypto user in the documentation was
named with hyphens — `cu-web-outbound`, `cu-ca-hub-root`, `cu-ca-dfsp-root` — and all were rejected.
The error names the character rather than the field, so it reads as a problem with the command.
Fixed in 15 places; the per-tenant name now folds anything outside the allowed set, because an
fspId carrying a hyphen or a dot would have been rejected several steps into onboarding, after the
Vault writes.

**A key generated without `sign=true` looks entirely normal.** It lists, it shares, it carries the
right label — and fails only at the first signature, with `CKR_KEY_FUNCTION_NOT_PERMITTED`, which
reads like a permissions problem rather than an attribute nobody set. The scripts set it correctly;
a hand-typed command during this run did not. `extractable=false` sits in the same flag, so the same
slip produces a key that signs *and* can be exported — silently removing the reason for the profile.

**The token label cannot be chosen.** The device names its single token itself. Requiring operators
to look it up and copy it into configuration adds a value they cannot influence, so the slot lookup
now takes the only token when no label is set, and still requires one where several exist — which is
the SoftHSM case, a token per tenant.

**Generated passwords sit exactly at the device maximum.** 32 characters, limit 32. It works with no
margin, and the limit was not written down anywhere before this run.

## Signing throughput — measured, and it caps lower than expected

Signing an existing RSA-2048 key as the shared signing user, from a pod on a cluster node.

| Sessions in the pool | signatures/sec | ms per signature | longest event-loop stall |
| --- | --- | --- | --- |
| 1 | 345 | 2.90 | 9ms |
| **4** | **543** | **1.84** | 14ms |
| 8 | 281 | 3.56 | 49ms |
| 16 | 256 | 3.90 | 98ms |
| 32 | 271 | 3.68 | 164ms |

**Throughput peaks at four sessions and then falls**, which is the opposite of how a pool normally
behaves. The cause is that the binding offers **no asynchronous `C_SignInit`** — only `C_Sign` has
one — and against a network-attached device that call is a round trip. So each signature blocks the
event loop before its asynchronous half begins, and concurrent workers queue those blocking calls
against the single thread. The stall column is the evidence: it grows roughly linearly with pool
size.

**`UV_THREADPOOL_SIZE` is not the limit here.** Raising it from 4 to 32 moved nothing — 543 to 502
at the best pool size, within noise. Against a local software module it *was* the ceiling, which is
why that assumption needed testing rather than carrying over.

**The ceiling for one process is therefore about 500–550/sec.** At the best pool size the per-call
cost falls from 2.9ms to 2.0ms and stops; that floor is `C_SignInit` serialising.

### What this means for capacity

At 80–100 TPS the hub-facing leg needs roughly **480–600 signatures/sec**, so **one replica does not
cover the target** — measured headroom was 0.9x.

**Scale horizontally.** Each replica holds its own sessions and its own login, so two replicas give
roughly 1,000/sec. Two are wanted for availability regardless, and this is a values change rather
than a code change.

**Worker threads are the fallback**, not the first answer. They would move `C_SignInit` off the
main thread and lift the per-process ceiling, at the cost of a real rewrite of the signing path.
Worth it only if a single pod ever has to exceed ~500/sec.

**What was NOT measured:** several tenants signing concurrently, and contention from other users of
the same cluster. Both are plausible and neither is covered by these figures.

## Still open

**Whether quorum or MFA get enabled later.** Both are off today and both would break the scripts.
Worth agreeing with whoever administers the cluster that turning either on is a coordinated change.

**Key destruction at offboarding.** The owner can delete, so the operation exists — but nothing
automates it, and the component holding each tenant's credential is the one that would have to.
